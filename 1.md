1. Проверяем логи Apache
Если у вас по-прежнему используется связка Nginx + Apache (mod_php), диагностику нужно начинать именно с Apache.
tail -f /var/log/httpd/error_log


Или:
journalctl -u httpd -f


Откройте страницу обновлений повторно:
/bitrix/admin/update_system.php


Ищите сообщения, предшествующие TypeError:
fopen(): Failed to open stream: Permission denied
fopen(): Failed to open stream: No such file or directory
fopen(): open_basedir restriction in effect
fopen(): Failed to open stream: Read-only file system


Разработчики Битрикса могли подавить вывод предупреждения от fopen() через оператор @. В таком случае используем strace (см. пункт 5).
2. Проверяем права на файлы и каталоги
В первую очередь я бы проверил следующие файлы и каталоги:
cd /var/www/html

ls -ld bitrix
ls -ld bitrix/updates
ls -ld bitrix/modules/main
ls -l bitrix/license_key.php
ls -l bitrix/modules/main/classes/general/update_client.php


Определяем, от какого пользователя работает Apache:
ps -eo user,group,pid,comm | grep httpd


Проверяем доступ на запись (предполагаем, что Apache работает от пользователя apache):
sudo -u apache bash -c '
for p in \
/var/www/html/bitrix \
/var/www/html/bitrix/updates \
/var/www/html/bitrix/license_key.php \
/var/www/html/bitrix/modules/main \
/tmp
do
    if test -w "$p"; then
        echo "OK: $p"
    else
        echo "FAIL: $p"
    fi
done'


Проверка файлов лицензии — гипотеза на основании названия метода __ApplyLicenseInfo. Точный файл пока неизвестен.

Не рекомендую сразу выполнять рекурсивный chmod 777 или chown всего портала.
3. Проверяем SELinux
Особенно актуально, если портал работает на РЕД ОС, RHEL или аналогичном дистрибутиве.
getenforce


ausearch -m AVC,USER_AVC -ts recent


Проверяем контексты:
ls -Zd /var/www/html/bitrix
ls -Zd /var/www/html/bitrix/updates
ls -Z /var/www/html/bitrix/license_key.php


Даже при корректных UNIX-правах SELinux может запрещать запись от имени Apache.
4. Проверяем файловую систему и PHP
df -h /var/www/html /tmp
df -i /var/www/html /tmp
findmnt -T /var/www/html


Проверяем настройки PHP:
php -v
php --ini


php -i | grep -E \
'open_basedir|upload_tmp_dir|sys_temp_dir|error_log|log_errors|disable_functions'


Важно: настройки PHP CLI могут отличаться от настроек mod_php в Apache. Поэтому дополнительно проверьте соответствующие параметры через административный раздел Битрикс24.
5. Точно определяем проблемный файл через strace
Это наиболее эффективный способ диагностики в данном случае, особенно если файл update_client.php обфусцирован и весь PHP-код находится на первой строке.

Запустите от root:
strace -f -s 256 -e trace=%file \
$(pgrep -x httpd | sed 's/^/-p /') \
-o /tmp/bitrix-update.trace


После запуска:
1. Откройте страницу обновлений Битрикс24.
2. Дождитесь появления ошибки.
3. Остановите strace через Ctrl+C.
4. Выполните:
grep -E 'EACCES|EPERM|EROFS|ENOSPC|EDQUOT' \
/tmp/bitrix-update.trace


Дополнительно:
grep -E 'O_WRONLY|O_RDWR|O_CREAT' \
/tmp/bitrix-update.trace | tail -100


Расшифровка ошибок:
Ошибка	Причина
EACCES	Недостаточно прав или ограничения SELinux
EPERM	Операция запрещена
EROFS	Файловая система только для чтения
ENOSPC	Нет свободного места или inode
ENOENT	Файл или каталог отсутствует
EDQUOT	Превышена дисковая квота

На нагруженном production-портале запускайте трассировку кратковременно.
6. Проверяем совместимость версии ядра с PHP 8.3
Узнаём версию главного модуля:
cat /var/www/html/bitrix/modules/main/install/version.php


Битрикс официально указывает, что причиной ошибок после перехода на PHP 8.x может быть отсутствие предварительного обновления ядра и модулей платформы. 
helpdesk.bitrix24.ru+1


Документация: Переход на PHP 8.x в коробочных версиях Битрикс24.

Если права и файловая система в порядке, необходимо проверить совместимость конкретной версии main с PHP 8.3.
7. Что рекомендую сделать в первую очередь
Пришлите результаты следующих команд:
cat /var/www/html/bitrix/modules/main/install/version.php

php -v

ps -eo user,group,pid,comm | grep httpd

ls -ld /var/www/html/bitrix{,/updates}

ls -l /var/www/html/bitrix/license_key.php

getenforce

df -h /var/www/html

df -i /var/www/html


Моя основная гипотеза — невозможность открытия файла на запись при сохранении лицензионной информации.

Я бы пока не откатывал PHP 8.3, не увеличивал memory_limit и не изменял исходный код update_client.php. Сначала необходимо установить первопричину через права доступа и strace.
