1. Проверяем пользователя, от которого выполняется PHP
Поскольку файлы принадлежат пользователю и группе bitrix:bitrix, предполагаю, что Apache или PHP-FPM работает от другого пользователя.

Проверяем конкретный процесс из вашей трассировки:
ps -p 3670238 -o pid,ppid,user,group,comm,args


cat /proc/3670238/status | grep -E '^(Name|Uid|Gid|Groups):'


Если процесс уже завершился:
ps -eo pid,ppid,user,group,comm | grep -E 'httpd|php-fpm'


Также проверяем настройки Apache:
grep -RniE '^\s*(User|Group)\s+' /etc/httpd/


И PHP-FPM, если он используется:
grep -RniE '^\s*(user|group)\s*=' /etc/php-fpm.d/

3. Варианты исправления
Вариант A. Добавить apache в группу bitrix
Если Apache действительно работает от пользователя apache и именно такой пользователь предусмотрен вашей архитектурой:
usermod -aG bitrix apache


Проверяем:
id apache


Перезапускаем Apache, чтобы рабочие процессы получили новый список групп:
systemctl restart httpd


Если используется PHP-FPM от пользователя apache, потребуется перезапустить и соответствующую службу PHP-FPM.

Этот вариант сработает, если необходимые файлы и каталоги доступны группе bitrix на запись.
Вариант B. Вернуть выполнение PHP от пользователя bitrix
Если до обновления PHP портал работал от пользователя bitrix, а после обновления начал работать от apache, лучше восстановить первоначальную конфигурацию.

Для Apache с mod_php:
User bitrix
Group bitrix


Для PHP-FPM в конфигурации соответствующего пула:
user = bitrix
group = bitrix


Перед изменением необходимо убедиться, что на сервере нет других сайтов, которым требуется выполнение PHP от другого пользователя.

1. Проверяем, кто фактически выполняет PHP
Выполните:
httpd -M 2>&1 | grep -Ei 'php|proxy|mpm'


ps -eo pid,ppid,user,comm,args | grep -E 'httpd|php-fpm' | grep -v grep


Не исключено, что после перехода на PHP 8.3 обработка PHP осуществляется через PHP-FPM, а не через mod_php.

В таком случае трассировка только Apache не покажет файловые операции PHP.
2. Запускаем расширенную трассировку
Будем отслеживать одновременно Apache и PHP-FPM, включая дочерние процессы и сетевые подключения.

От пользователя root:
strace -f -tt -s 512 -yy \
-e trace=%file,socket,connect \
$(pgrep -x 'httpd|php-fpm' | sed 's/^/-p /') \
-o /tmp/bitrix-update-full.trace


Откройте страницу обновлений, воспроизведите ошибку и остановите strace через Ctrl+C.

Затем выполните:
grep -E 'O_WRONLY|O_RDWR|O_CREAT' \
/tmp/bitrix-update-full.trace


grep -E 'EACCES|EPERM|EROFS|ENOSPC|EDQUOT' \
/tmp/bitrix-update-full.trace


3. Проверяем настройки PHP
Если fopen() блокируется на уровне самого PHP, системный вызов открытия файла может вообще не произойти. Соответственно, strace его не покажет.
php -i | grep -E \
'open_basedir|allow_url_fopen|sys_temp_dir|upload_tmp_dir'


Также проверяем конфигурационные файлы:
grep -RniE \
'open_basedir|allow_url_fopen|sys_temp_dir|upload_tmp_dir' \
/etc/php.ini /etc/php.d/ /etc/httpd/ /etc/php-fpm.d/ \
2>/dev/null


Особое внимание:
Параметр	Что проверить
open_basedir	Нет ли ограничений на доступ к нужным каталогам
allow_url_fopen	Не запрещено ли открытие удалённых ресурсов
sys_temp_dir	Существует ли каталог и доступен ли на запись
upload_tmp_dir	Корректность временного каталога
